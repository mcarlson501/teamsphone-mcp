# `v0.1.0` external release test plan

This is the final acceptance plan for the first tagged release. Run it from a clean
release-candidate source archive on an Ubuntu machine outside the development workspace.
Use only a dedicated non-production Microsoft 365 tenant and synthetic identities,
numbers, queues, and audit data.

Do not create the `v0.1.0` tag until every required gate below passes and the evidence
has been reviewed. A failed write restoration, credential leak, tenant-isolation defect,
or bypass of a what-if ceiling is release-blocking.

## Release acceptance criteria

| ID | Required result |
| --- | --- |
| M65-SETUP-01 | A clean Ubuntu host needs only Docker Engine with Compose v2, the source archive, and this documentation to prepare the server. |
| M65-SETUP-02 | `init prepare` generates a one-year client-auth certificate, `.env`, bearer token, and signing key without printing secret material. |
| M65-SETUP-03 | The certificate directory is mode `0700`; `.env` and the PFX are mode `0600`. Neither path is inside source control history or the audit volume. |
| M65-SETUP-04 | The generated configuration defaults to `TEAMSPHONE_MCP_MODE=whatif` and passes `docker compose config --quiet`. |
| M65-SETUP-05 | The printed Entra instructions identify the generated public certificate, thumbprint, Graph permissions, admin consent, and Teams role. |
| M65-SETUP-06 | After portal setup, `init verify` starts the server and completes a real `get-user-voice-config` call with a correlation ID. |
| M65-VSCODE-01 | VS Code connects over Streamable HTTP using a securely prompted bearer token and discovers 38 tools from server version `0.1.0`. |
| M65-SAFETY-01 | The checked-in safety demo proves dry-run, parameter-mismatch refusal, exact confirmed execution, audit retrieval, and tokenless session what-if. |
| M65-SAFETY-02 | With the Compose default ceiling, a real tenant write request returns `simulated: true`, issues no confirmation token, and changes no tenant state. |
| M65-SAFETY-03 | In an explicitly enabled full-mode test, a dedicated fixture completes dry-run, confirmed execution, verification, and restoration to its baseline. |
| M65-AUDIT-01 | Read, dry-run, refused, simulated, executed, and restoration calls are queryable by tenant and their correlation IDs survive a container restart. |
| M65-SECURITY-01 | Missing and incorrect bearer tokens receive `401`; no tool list or credential material is returned. |
| M65-SECURITY-02 | Host, container, and audit logs contain no bearer token, signing key, PFX password, private key, JWT, or full certificate thumbprint. |
| M65-RELEASE-01 | Offline suites, container smoke tests, the safety demo, and all applicable live suites pass from the same candidate commit. |

## Test topology

Preferred topology:

1. Ubuntu 24.04 LTS host or VM with Docker Engine and Compose v2.
2. VS Code connected to that host through Remote-SSH.
3. TeamsPhone MCP bound to `127.0.0.1:5199` on Ubuntu.
4. Dedicated demo tenant with no production identities or numbers.

With Remote-SSH, create the MCP configuration in the remote workspace or run
**MCP: Open Remote User Configuration** so `127.0.0.1` resolves on Ubuntu. If VS Code
runs only on another computer, keep the server bound to loopback and create a tunnel:

```bash
ssh -L 5199:127.0.0.1:5199 <ubuntu-user>@<ubuntu-host>
```

Do not expose port 5199 directly to a LAN or the internet for this release test.

## Fixtures and evidence

Prepare these tenant fixtures before the write phases:

- one ordinary demo user for read tests;
- one numbered, voice-enabled source user;
- one voice-licensed target user with no assigned number;
- one ineligible target, such as a resource account, for a negative preflight;
- one isolated Phase D user that satisfies the prerequisites in [testing.md](testing.md);
- optionally one call queue, auto attendant, and traceable service number.

Record values only in the ignored `.env.integration` on Ubuntu. Do not paste tenant IDs,
UPNs, phone numbers, tokens, certificate paths, or screenshots containing them into an
issue, pull request, release note, or tracked test report.

Create an evidence directory outside the source tree. For each phase capture:

- date/time and candidate commit SHA;
- pass/fail and command used;
- correlation IDs with tenant data removed;
- sanitized error codes for expected refusals;
- before/after tenant state for the write and restoration phases;
- sanitized VS Code MCP output and container logs.

## Phase 0: clean candidate acquisition

Use a release-candidate commit that contains all intended `v0.1.0` changes. Download its
GitHub source archive rather than copying the development workspace. Record its checksum:

```bash
candidate_sha='<full-commit-sha>'
curl --fail --location \
  "https://github.com/mcarlson501/teamsphone-mcp/archive/${candidate_sha}.tar.gz" \
  --output teamsphone-mcp-v0.1.0-rc.tar.gz
sha256sum teamsphone-mcp-v0.1.0-rc.tar.gz
mkdir teamsphone-mcp-v0.1.0-rc
tar --extract --gzip \
  --file teamsphone-mcp-v0.1.0-rc.tar.gz \
  --directory teamsphone-mcp-v0.1.0-rc \
  --strip-components 1
cd teamsphone-mcp-v0.1.0-rc
mkdir ../evidence
```

Confirm that no local development files were carried across:

```bash
test ! -e .env
test ! -e .env.integration
test ! -d audit
if find . -type f \( -name '*.pfx' -o -name '*.key' \) -print -quit | grep -q .; then
  echo 'error: private key material exists in the source archive' >&2
  exit 1
fi
```

Record the platform and Docker baseline:

```bash
uname -a
cat /etc/os-release
docker version
docker compose version
```

**Pass:** the archive is clean, the candidate SHA is recorded, and Docker commands work
without elevated interactive access.

## Phase 1: Entra registration and guided preparation

Create a single-tenant Entra app as described in [setup-entra-app.md](setup-entra-app.md),
then note the directory tenant ID and application client ID. Do not create a client
secret.

Run the Docker-only preparation command:

```bash
./scripts/init.sh prepare \
  --tenant-id '<directory-tenant-id>' \
  --client-id '<application-client-id>'
```

Verify the generated controls without displaying file contents:

```bash
stat --format '%a %n' .env ~/.config/teamsphone-mcp/teamsphone-mcp-default.pfx
stat --format '%a %n' ~/.config/teamsphone-mcp
grep --quiet '^TEAMSPHONE_MCP_MODE=whatif$' .env
docker compose --env-file .env config --quiet
```

Expected modes are `600`, `600`, and `700`, respectively. Confirm the command output
contains the public `.cer` path, subject, thumbprint, expiry, permissions, consent, and
role instructions, but none of the generated secret values.

In Entra:

1. Upload the generated public `.cer` to the app registration.
2. Grant `User.Read.All` and `Organization.Read.All` application permissions.
3. Add `CallRecords.Read.All` if the M5.5 call-record tests will run.
4. Grant tenant admin consent.
5. Assign Teams Communications Administrator to the service principal.
6. Wait for certificate, consent, and role propagation.

**Stop:** do not proceed if a client secret was created, private key material left the
Ubuntu host, or generated secret values appeared in captured output.

## Phase 2: connectivity self-test

Use a real synthetic user from the demo tenant:

```bash
./scripts/init.sh verify --user-upn 'demo.user@example.com'
```

The command must:

- validate Compose;
- build and start the local container;
- observe the unauthenticated `401` gate;
- initialize an authenticated MCP session;
- return `Succeeded` from `get-user-voice-config`; and
- print a correlation ID while confirming the server remains in `whatif` mode.

Inspect runtime state:

```bash
docker compose ps
docker compose exec teamsphone-mcp id
docker inspect --format '{{.State.Health.Status}}' "$(docker compose ps -q teamsphone-mcp)"
docker compose logs --no-color --tail 200 teamsphone-mcp > ../evidence/container-startup.log
```

**Pass:** the container is healthy, runs as a non-root user, the real tenant read passes,
and the saved log is free of credential material.

## Phase 3: HTTP authentication checks

Without a bearer token:

```bash
curl --silent --output /dev/null --write-out '%{http_code}\n' \
  --request POST http://127.0.0.1:5199/mcp
```

Repeat with `Authorization: Bearer deliberately-wrong`. Both responses must be `401` and
must not contain a tool list.

Run the repository log gate from a checkout with the .NET SDK available:

```bash
./scripts/log-scrubber-check.sh
```

**Pass:** both negative requests return `401`, the log scrubber passes, and no secret is
present in saved output.

## Phase 4: VS Code MCP configuration

Use a secure VS Code input rather than putting the bearer token in `mcp.json`. In a
throwaway remote workspace, create `.vscode/mcp.json`:

```json
{
  "servers": {
    "teamsphoneMcp": {
      "type": "http",
      "url": "http://127.0.0.1:5199/mcp",
      "headers": {
        "Authorization": "Bearer ${input:teamsphone-mcp-bearer}"
      }
    }
  },
  "inputs": [
    {
      "type": "promptString",
      "id": "teamsphone-mcp-bearer",
      "description": "TeamsPhone MCP bearer token",
      "password": true
    }
  ]
}
```

Retrieve the bearer value from `.env` only when VS Code prompts for it. Do not paste it
into the JSON file or chat.

1. Run **MCP: List Servers**.
2. Select `teamsphoneMcp`, confirm trust, and start it.
3. Open the server tools and confirm exactly 38 tools are discovered.
4. Enable only the tools needed for each test phase.
5. Use **Show Output** to confirm initialization reports `TeamsPhoneMcp.Host 0.1.0`.

Run these low-risk calls from Copilot Agent mode and preserve their correlation IDs:

1. `ping` with a synthetic message.
2. `get-user-voice-config` for the demo user.
3. `list-phone-numbers` with a small page size.
4. `diagnose-user-voice` for the demo user.
5. `run-tenant-health-check`.
6. `query-audit-log` for the current tenant and today's UTC range.

Review every proposed tool invocation before approving it. Verify outputs contain the
expected tenant's synthetic data and never another tenant's values.

**Pass:** VS Code remains connected, finds 38 tools, reports version `0.1.0`, all six
calls return structured envelopes, and each call appears in the audit query.

## Phase 5: reproducible synthetic safety demonstration

Run:

```bash
./scripts/demo-safety.sh
```

Expected ordered proof:

1. `dryRunCompleted`, `simulated=false`, confirmation token issued;
2. changed parameters rejected with `invalidConfirmationToken`;
3. exact confirmed plan returns `succeeded`;
4. execution correlation ID found in the audit trail;
5. session what-if returns `simulated=true` with no confirmation token.

This phase uses only `mock-write-user-policy`; it must not contact Microsoft 365. Compare
its output with [the checked-in recording](assets/safety-demo.cast).

## Phase 6: real tenant what-if ceiling

Keep `TEAMSPHONE_MCP_MODE=whatif`. Through VS Code, call a real write tool against a
dedicated fixture and explicitly request `dryRun: false`. Prefer
`move-number-between-users` with the isolated source and target fixture used by the live
integration suite.

Required result:

- status is `DryRunCompleted`;
- `dryRun` and `simulated` are `true`;
- `confirmationToken` is null or absent;
- only snapshot, preflight, and dry-run stages ran; and
- the source user, target user, number inventory, and policies remain unchanged.

Repeat with a named client configured using
`Auth__ClientPolicy__inspector__WhatIfMode=true` while the server is otherwise in full
mode. The same tokenless simulated result must hold for that client, while an unrestricted
client can still receive a normal dry-run token.

For this test, create `../evidence/compose.inspector.yaml` outside the source tree. It
contains only environment interpolation, not the token itself. The explicit `full`
override is required to prove the client policy independently of the normal server-wide
`whatif` default:

```yaml
services:
  teamsphone-mcp:
    environment:
      TEAMSPHONE_MCP_MODE: full
      Auth__ClientTokens__inspector: ${TEAMSPHONE_MCP_INSPECTOR_BEARER_TOKEN:?Set inspector token}
      Auth__ClientPolicy__inspector__WhatIfMode: "true"
```

Export a fresh random token and start with both Compose files:

```bash
export TEAMSPHONE_MCP_INSPECTOR_BEARER_TOKEN="$(openssl rand -hex 32)"
docker compose \
  -f docker-compose.yml \
  -f ../evidence/compose.inspector.yaml \
  up --detach --force-recreate
```

Use that token in a second secure VS Code input/server entry, run the simulated write,
then restore the default `whatif` deployment and unset the token after the test:

```bash
docker compose -f docker-compose.yml up --detach --force-recreate
unset TEAMSPHONE_MCP_INSPECTOR_BEARER_TOKEN
rm ../evidence/compose.inspector.yaml
```

**Stop:** any real tenant mutation or issued confirmation token under either ceiling is a
release-blocking security defect.

## Phase 7: offline source validation on Ubuntu

Install the .NET 8 SDK, PowerShell 7.4, and Gitleaks 8.30.1. Install the test modules:

```bash
pwsh -NoProfile -c 'Install-Module Pester -RequiredVersion 6.0.0 -Scope CurrentUser -Force -SkipPublisherCheck'
pwsh -NoProfile -c 'Install-Module PSScriptAnalyzer -RequiredVersion 1.25.0 -Scope CurrentUser -Force -SkipPublisherCheck'
```

Then run:

```bash
dotnet restore TeamsPhoneMcp.sln --locked-mode
dotnet format TeamsPhoneMcp.sln --verify-no-changes --no-restore
dotnet build TeamsPhoneMcp.sln --configuration Release --no-restore
dotnet test TeamsPhoneMcp.sln --configuration Release --no-build \
  --filter 'FullyQualifiedName!~IntegrationTests'
pwsh -NoProfile -c 'Invoke-Pester -Path tools -CI -Output Detailed'
pwsh -NoProfile -c 'Invoke-Pester -Path scripts/analyzer -CI -Output Detailed'
pwsh -NoProfile -File scripts/lint-tools.ps1
gitleaks dir --redact --verbose --no-banner .
./scripts/log-scrubber-check.sh
./scripts/demo-safety.sh
```

Also verify the dependency graph:

```bash
dotnet list TeamsPhoneMcp.sln package --vulnerable --include-transitive
```

**Pass:** every command exits zero, the Release build has no warnings, and NuGet reports
no vulnerable direct or transitive packages.

## Phase 8: gated live integration suites

Install the pinned MicrosoftTeams module version:

```bash
pwsh -NoProfile -c 'Install-Module MicrosoftTeams -RequiredVersion 7.8.0 -Scope CurrentUser -Force'
```

Populate the ignored
`.env.integration` from `.env.integration.template`. Follow the fixture requirements in
[testing.md](testing.md). Source it and run each suite separately so a failure has a clear
scope:

```bash
set -a
source .env.integration
set +a

./scripts/live-test.sh --filter FullyQualifiedName~PhaseAIntegration -l 'console;verbosity=detailed'
./scripts/live-test.sh --filter FullyQualifiedName~M55IntegrationTests -l 'console;verbosity=detailed'
./scripts/live-test.sh --filter FullyQualifiedName~MoveNumberIntegration -l 'console;verbosity=detailed'
./scripts/live-test.sh --filter FullyQualifiedName~PhaseDIntegrationTests -l 'console;verbosity=detailed'
```

Required results:

- Phase A reads all succeed and produce one scrubbed audit record per call.
- M5.5 diagnostics and reports complete; unavailable tenant fixtures skip only the
  explicitly documented optional cases.
- The move-number test executes, verifies, and moves the number back to its baseline.
- The Phase D offboard/onboard round trip restores the original user and inventory state.
- The ineligible-target preflight performs no write and issues no token.

**Stop:** if a restoration fails, preserve the sanitized envelope and audit correlation
ID, restore the fixture manually from `diff.before`, and do not run another write test
until tenant state is confirmed.

## Phase 9: audit persistence and restart

Use `query-audit-log` and `get-change-detail` to retrieve records from the preceding
phases. Record correlation IDs for at least one read, refusal, simulation, successful
write, and restoration.

Restart without deleting the volume:

```bash
docker compose restart teamsphone-mcp
docker compose ps
```

Reconnect VS Code and query the same records again.

**Pass:** all selected records and snapshots remain available after restart, and no
credential material appears in the JSONL files or snapshots.

## Phase 10: cleanup and release decision

1. Confirm all write fixtures match their recorded baseline.
2. Export the sanitized acceptance evidence.
3. Stop the server with `docker compose down`; do not delete the audit volume until
   evidence review is complete.
4. Remove the VS Code server entry or clear its securely stored input.
5. Revoke/delete the test certificate or app registration if it will not be retained for
   future demo-tenant testing.

The release is ready to tag only when:

- every required acceptance ID is marked pass;
- there are no unresolved severity-high or release-blocking findings;
- the candidate commit tested is exactly the commit to tag;
- CI is green on that commit;
- the changelog date replaces `Unreleased`; and
- the signed annotated tag and GitHub prerelease are created from protected `main`.
